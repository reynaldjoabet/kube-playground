# Kubernetes Networking

Deep dive on how Service traffic is actually routed: kube-proxy, iptables chains (KUBE-SERVICES / KUBE-SVC / KUBE-SEP), NAT, conntrack, and LoadBalancer.

See also: [`kubernetes.md`](kubernetes.md) (architecture overview) · [`rbac-and-identity.md`](rbac-and-identity.md) · [`cloud-kubernetes.md`](cloud-kubernetes.md)

### Pod-to-Pod Networking (The CNI's Job)
When you create a Pod, it needs a real IP address and network routes so it can talk to other Pods.

### Service Load Balancing (kube-proxy's Job)
Pods are ephemeral. If a Pod dies and comes back, its IP address changes. To solve this, you create a `Service`, which provides a stable, virtual IP (ClusterIP).

`iptables-save -t nat` or `iptables -t nat -L` on any Kubernetes worker node running `kube-proxy`  
`kube-proxy `essentially abuses the Linux kernel's Network Address Translation (NAT) table to build a distributed load balancer

### The Global Intercept (KUBE-SERVICES chain)
All traffic that touches the node's network stack first passes through the `PREROUTING` chain (for incoming packets from an interface) or the `OUTPUT` chain (for packets generated locally on the node). Both immediately jump to a custom Kubernetes chain called `KUBE-SERVICES` — the single, per-node entry point for all service routing.

`kube-proxy writes a rule here that says: "If a packet is destined for the fake ClusterIP 10.96.0.100 on port 80, jump to a specific Service chain."`.  
`-A KUBE-SERVICES -d 10.96.0.100/32 -p tcp -m tcp --dport 80 -j KUBE-SVC-4N57TF3SQZZZZZZZ`.  
(The `4N57TF3SQZZZZZZZ`... is a hash generated by K8s based on the Service name and namespace).

`1 service-port  →  1 KUBE-SVC-* chain  +  N KUBE-SEP-* chains (one per Pod endpoint)`

A Service with multiple ports gets one `KUBE-SVC-*` chain per port — that's why `kube-dns` appears 3 times in `KUBE-SERVICES` (`dns-tcp`, `metrics`, `dns/udp`). Each port is treated as a separate routing target.

So at scale, with 100 services averaging 3 pods each, you'd have ~100 `KUBE-SVC-*` chains and ~300 `KUBE-SEP-*` chains. This is why large clusters can have iptables tables with thousands of rules — and why IPVS mode was introduced as a more scalable alternative.

### The Load Balancer (KUBE-SVC-... chain)
This chain acts as the actual load balancer. If a service is backed by 2 Pods, `kube-proxy` uses the `iptables statistic` module to distribute traffic randomly.
```sh
# Give the first Pod a 50% chance of receiving the packet
-A KUBE-SVC-4N57TF3SQZZZZZZZ -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-W5KXYZ1234567890

# If the first rule didn't trigger, the remaining 50% always hits the second Pod
-A KUBE-SVC-4N57TF3SQZZZZZZZ -j KUBE-SEP-ABCDEF9876543210
```
```sh
           100 packets
               │
        ┌──────┴──────┐
       33%            67%
        │              │
      Pod 1     ┌──────┴──────┐
               50%           50%
                │              │
              Pod 2          Pod 3
              
       33        33            34     ≈ equal split
```
```sh

  ┌───┴───┐

  │       │

       │     │

```
The probability at each rule is `1 / (number of pods remaining)`
                                                     
###  Destination NAT (KUBE-SEP-... chain)
"SEP" stands for Service EndPoint. This chain does the actual magic. It rewrites the destination IP address of the packet (DNAT) from the fake ClusterIP to the real Pod IP.

Let's say the 50% probability hit the first Pod:
```sh
# (Optional) Source NAT if the Pod is trying to talk to its own Service (Hairpin NAT)
-A KUBE-SEP-W5KXYZ1234567890 -s 10.244.1.10/32 -j KUBE-MARK-MASQ 

# The actual DNAT translation! Change the destination to 10.244.1.10:80
-A KUBE-SEP-W5KXYZ1234567890 -p tcp -m tcp -j DNAT --to-destination 10.244.1.10:80
```

`target                      = where to jump (-j)`

The target column can be:   
 1. **Built-in terminating targets — stop processing, never return**:
- ACCEPT   - let the packet through
- DROP     - silently discard
- REJECT   - discard and send error back to sender  
2. **Built-in modifying targets — perform an action then continue**:
- DNAT       - rewrite destination IP/port (used by KUBE-SEP-*)
- SNAT       - rewrite source IP/port
- MASQUERADE - like SNAT but auto-detects the outgoing interface IP
- MARK       - tag the packet with a value (used by KUBE-MARK-MASQ)
- RETURN     - stop traversing current chain, go back to parent chain
- LOG        - log the packet, then continue
3. **User-defined chains — jump into a sub-chain, return if no match**:
- KUBE-SERVICES
- KUBE-SVC-xxx
- KUBE-SEP-xxx
- KUBE-NODEPORTS
- DOCKER

`-j KUBE-SERVICES` is a jump, not a terminating rule. The difference:

`-j KUBE-SERVICES `(jump) — goes into the sub-chain, and if no rule there matches, returns back to `PREROUTING` and continues to the next rule (`DOCKER_OUTPUT`, `DOCKER`, etc.)

`-j ACCEPT / -j DROP` (terminating) — stops processing entirely, never returns

Only if `KUBE-SERVICES` finds a matching ClusterIP and does a `DNAT` does the packet exit without returning. For all other traffic (normal internet requests, pod-to-pod direct, etc.) `KUBE-SERVICES` finds no match and quietly hands control back to `PREROUTING`

`KUBE-SERVICES` has 2 references — meaning it's jumped to from both `PREROUTING` (for incoming traffic) and `OUTPUT` (for traffic originating on the node itself):

```sh
Chain PREROUTING
  KUBE-SERVICES  ← all external traffic enters here

Chain OUTPUT
  KUBE-SERVICES  ← all locally-generated traffic enters here

```
Every packet on the node — whether from a Pod, kubelet, or incoming from the network — passes through that one `KUBE-SERVICES` dispatch table.

So every packet enters KUBE-SERVICES. The question is what happens inside `KUBE-SERVICES`: 
```sh
Chain KUBE-SERVICES
  10.96.0.1   tcp dpt:443   → KUBE-SVC-NPX46M4PTMTKRN6Y
  10.96.0.10  tcp dpt:53    → KUBE-SVC-ERIFXISQEP7F7OF4
  10.96.0.10  tcp dpt:9153  → KUBE-SVC-JD5MR3NA4I4DYORP
  10.96.0.10  udp dpt:53    → KUBE-SVC-TCOU7JCQXEZGVUNU
  ADDRTYPE dst-type LOCAL   → KUBE-NODEPORTS   ← last rule
  ```
Inside `KUBE-SERVICES` the rules are specific (match exact ClusterIP + port). If none match, the chain ends and netfilter returns to `PREROUTING` — so `DOCKER_OUTPUT` and `DOCKER `do still run for non-ClusterIP traffic.

So the correction is: `DOCKER_OUTPUT` and `DOCKER` do still run, but only because the rules inside KUBE-SERVICES didn't match 

In Kubernetes iptables-based proxying (kube-proxy in iptables mode), `KUBE-SERVICES` has one entry per `Service IP:port `combination. 
For each Service, kube-proxy adds a rule like: `-A KUBE-SERVICES -d <ClusterIP>/32 -p tcp --dport <port> -j KUBE-SVC-<hash>`
So if you have 3 services, each with 1 port, you get 3 rules in `KUBE-SERVICES`. If a service exposes multiple ports, you get one rule per port.

Each of those rules jumps to a per-service chain (`KUBE-SVC-<hash`>), which then load-balances across the endpoints via `KUBE-SEP-<hash>` chains (one per endpoint/pod).

 By the time a packet reaches `KUBE-SEP-*`, it has already been filtered by the chain above it.

The journey is:
```sh
KUBE-SERVICES  →  matched on ClusterIP + port  →  KUBE-SVC-*
KUBE-SVC-*     →  load balanced                →  KUBE-SEP-*
KUBE-SEP-*     →  DNAT to real Pod IP
```
By the time you're inside `KUBE-SEP-*`, the ClusterIP check already happened at `KUBE-SERVICES`. Only packets destined for that specific ClusterIP+port ever reached this chain. There's no need to check again — it would be redundant.

### Pod calls the API server (kubernetes service)
```sh
┌───────────────────────┐
│  API Server Process   │  ← listens on master_node_IP:6443
│  (running on masters) │
└───────────┬───────────┘

            ↓
┌──────────────────────────────────┐
│  Service "kubernetes" (default)  │
│  ClusterIP: 10.96.0.1            │

               │ by EndpointReconciler
               ↓
┌───────────────────────────────────────────────────┐

└───────────────────────────────────────────────────┘
```

Normal services use a label selector to find pods. The kubernetes Service has no selector — meaning the Endpoints controller does not populate it automatically.

*Endpoints are managed manually by the API server*:
`c.EndpointReconciler.ReconcileEndpoints(kubernetesServiceName, c.PublicIP, endpointPorts, reconcile)`

Each API server instance reconciles its own IP into the Endpoints list. When you have 3 master nodes, each kube-apiserver process adds itself to the Endpoints.

*The endpoints are master node IPs, not pod IPs*
The API server typically runs as a static pod with `hostNetwork: true`, so it binds to the master node's IP directly. The Endpoints object stores `c.PublicIP` — the master node's IP.

The API server is exposed inside the cluster as a regular Service — the kubernetes Service in the default namespace. It's the first thing that gets created when a cluster starts.
A pod hits `https://kubernetes.default.svc:443` → resolves to 10.96.0.1:443

```sh
ClusterIP (10.96.0.1:443)
    │

    │

```

Namespaces and Services are cluster-wide, not node-bound: resources (Namespaces, Services, Pods, etc.) are not "on" specific nodes. They live in etcd, the cluster-wide database. The API server is the only thing that `reads/writes` etcd.
```sh

                             ↑
              API Server (only reader/writer)
                 ↗            ↑            ↖

             │worker│     │worker│     │master│

```			
So the kubernetes Service is accessible from every node in the cluster — every pod on every worker node can resolve `kubernetes.default.svc.cluster.local` and reach the API server.

Always. `DNAT` first, `SNAT` second.
```sh
Packet arrives
    │
    ▼
PREROUTING ← DNAT here (rewrite destination)
    │
    ▼
Routing decision (kernel uses the NEW destination to decide where to send)
    │
    ▼
FORWARD (filter — allow/deny)
    │
    ▼
POSTROUTING ← SNAT here (rewrite source)
    │
    ▼
Packet leaves
```
Hooks have tables, and tables have chains/rules.   
`PREROUTING → INPUT → FORWARD → OUTPUT → POSTROUTING`.  
At each hook, multiple tables get a chance to process the packet, in a fixed order:
```sh
PREROUTING hook:
  1. raw table runs
  2. mangle table runs
  3. nat table runs          ← DNAT happens here

FORWARD hook:
  1. mangle table runs
  2. filter table runs       ← allow/deny here

POSTROUTING hook:
  1. mangle table runs
  2. nat table runs          ← SNAT happens here
```
Each table is split into chains, one per hook it participates in:
```sh
nat table:
  ├── PREROUTING chain    (DNAT)
  ├── INPUT chain
  ├── OUTPUT chain        (DNAT for local packets)
  └── POSTROUTING chain   (SNAT)

filter table:
  ├── INPUT chain         (allow/deny incoming)
  ├── FORWARD chain       (allow/deny forwarded)
  └── OUTPUT chain        (allow/deny outgoing)
```
`Hooks are positions in the pipeline. Tables register their chains at those hooks. Chains contain rules.`

A hook is a fixed point in the kernel's packet processing path where registered callback functions are called for every packet that passes through.

Each table (filter, nat, mangle, etc.) registers handler functions (`nf_hook_ops`) at the hooks it cares about.The filter table registers at only 3 of the 5 hooks — `LOCAL_IN`, `FORWARD`, and `LOCAL_OUT` — because filtering forwarded/local traffic makes sense, but `PREROUTING`/`POSTROUTING` are reserved for other purposes (NAT, mangle).

When a packet hits one of these points, the kernel calls every registered handler in priority order. Each handler returns a verdict:
- `NF_ACCEPT` — let it continue
- `NF_DROP` — discard it
- `NF_STOLEN` — handler took ownership, stop processing
- `NF_QUEUE` — send to userspace

Each hook point is assigned a number (its bit position):

```c
enum nf_inet_hooks {
	NF_INET_PRE_ROUTING,
	NF_INET_LOCAL_IN,
	NF_INET_FORWARD,
	NF_INET_LOCAL_OUT,
	NF_INET_POST_ROUTING,
	NF_INET_NUMHOOKS,
	NF_INET_INGRESS = NF_INET_NUMHOOKS,
};
```
```sh
NF_INET_PRE_ROUTING  = 0
NF_INET_LOCAL_IN     = 1
NF_INET_FORWARD      = 2
NF_INET_LOCAL_OUT    = 3
NF_INET_POST_ROUTING = 4
```
1 << N shifts the value 1 left by N positions, setting exactly that bit:
```sh
1 << 0  =  00001  (PRE_ROUTING)
1 << 1  =  00010  (LOCAL_IN)
1 << 2  =  00100  (FORWARD)
1 << 3  =  01000  (LOCAL_OUT)
1 << 4  =  10000  (POST_ROUTING)
```
`OR-ing `them together combines into one integer where each set bit means "this hook is active". The `filter` table:
```c
(1 << NF_INET_LOCAL_IN) | (1 << NF_INET_FORWARD) | (1 << NF_INET_LOCAL_OUT)
=  00010 | 00100 | 01000
=  01110   (decimal 14)
```
`The mangle table (all 5 hooks) = 11111 (decimal 31)`

The enum value is used as the shift amount
```sh
hook number (enum)  →  bit position in mask
0                   →  bit 0  =  00001
1                   →  bit 1  =  00010
2                   →  bit 2  =  00100
```

A bitmask lets you store multiple on/off flags packed into a single integer — one bit per flag.
Instead of having 5 separate booleans:
```sh
bool has_prerouting = true;
bool has_local_in   = false;
bool has_forward    = true;
...
```
You pack them all into one integer where each bit position represents one flag:
```sh
bit 4  bit 3  bit 2  bit 1  bit 0
  1      0      1      0      1
  POST  L_OUT  FWD   L_IN   PRE
```  
Then to set a flag you `OR it in`: `mask |= (1 << 2)`  
To check a flag you` AND it: if (mask & (1 << 2))` — nonzero means set  
To clear a flag: `mask &= ~(1 << 2)`

AND only produces a 1 where both inputs have a 1. So `mask & (1 << N)` isolates just that one bit — if it's set in the mask you get a nonzero result, if it's not set you get zero.

In the netfilter case, `valid_hooks` is just answering the question "which of these 5 hooks does this table care about?" — packed into one integer instead of five separate fields

you check one bit at a time. The whole point is that each bit is independent, so you `AND` with a mask that has exactly one bit set, which zeroes out everything else and leaves only the bit you care about.

`xt_hook_ops_alloc `does check one bit at a time — it shifts right each iteration and checks the lowest bit with `& 1`, because it needs to know which specific hooks to allocate ops for,
`& 1` means `AND with 00001` — it zeroes out every bit except bit 0 (the lowest):
```sh
01110 & 00001 = 00000  → lowest bit is 0
01111 & 00001 = 00001  → lowest bit is 1
```
User-defined chains (e.g. `iptables -N MYCHAIN`) are different — they have no corresponding hook. They only exist as jump targets within rule lists and are never registered as `nf_hook_ops`. Only the built-in chains correspond to hooks.

When `ipt_do_table` is called at a hook, it needs to find the right list of rules to walk. The table stores rules for each chain contiguously in memory, and uses the hook number as an index to find where that chain's rules start.

The table has an array `hook_entry[NF_INET_NUMHOOKS] `— indexed directly by hook number:
```sh
hook_entry[0]  →  offset to PREROUTING rules
hook_entry[1]  →  offset to INPUT rules
hook_entry[2]  →  offset to FORWARD rules
hook_entry[3]  →  offset to OUTPUT rules
hook_entry[4]  →  offset to POSTROUTING rules
```
A hook can have multiple tables registered at it — they run in priority order. For example at `NF_INET_LOCAL_IN:`
```sh
priority -150  →  raw table
priority -100  →  mangle table
priority   0   →  filter table
priority 100   →  nat table (INPUT chain)
```
Each table has exactly one chain per hook it's registered at. The filter table at `LOCAL_IN` gives you the` INPUT` chain. The mangle table at `LOCAL_IN` also gives you an `INPUT` chain — but it's a different chain in a different table, running at a different priority.

The packet hits `NF_INET_LOCAL_IN`. Four separate tables have registered at that hook, so the kernel calls each one in priority order:
```sh
1. raw table     → walks its INPUT chain    (your raw INPUT rules)
2. mangle table  → walks its INPUT chain    (your mangle INPUT rules)
3. filter table  → walks its INPUT chain    (your filter INPUT rules)
4. nat table     → walks its INPUT chain    (your nat INPUT rules)
```
Each table owns its own private rule blob completely independently.  
So the filter table and mangle table each have their own separate `xt_table_info` with their own `entries[]`:
```sh
filter table (xt_table)
└── private (xt_table_info)
    └── entries[]
        ├── hook_entry[1] → INPUT chain rules   (your -t filter INPUT rules)
        ├── hook_entry[2] → FORWARD chain rules
        └── hook_entry[3] → OUTPUT chain rules
```        
```sh
mangle table (xt_table)
└── private (xt_table_info)
    └── entries[]
        ├── hook_entry[0] → PREROUTING chain rules  (your -t mangle rules)
        ├── hook_entry[1] → INPUT chain rules
        ├── hook_entry[2] → FORWARD chain rules
        ├── hook_entry[3] → OUTPUT chain rules
        └── hook_entry[4] → POSTROUTING chain rules
```        
One table spans multiple hooks. A single `xt_table` registers at all the hooks listed in its `valid_hooks` bitmask.
For example the mangle table registers at all 5 hooks:
```sh
NF_INET_PRE_ROUTING  ──┐
NF_INET_LOCAL_IN     ──┤
NF_INET_FORWARD      ──┼──→  mangle table (one xt_table)
NF_INET_LOCAL_OUT    ──┤
NF_INET_POST_ROUTING ──┘
```
And the `filter` table registers at 3 hooks:
```sh
NF_INET_LOCAL_IN   ──┐
NF_INET_FORWARD    ──┼──→  filter table (one xt_table)
NF_INET_LOCAL_OUT  ──┘
```
At each hook, multiple tables can be present. So at `NF_INET_LOCAL_IN` for example, you have:
```sh
NF_INET_LOCAL_IN
├── raw table     (priority -150)
├── mangle table  (priority -100)
├── filter table  (priority   0)
└── nat table     (priority 100)
```
Each one is a separate `xt_table` with its own rule blob, but they all fire at the same hook — just in priority order. So the relationship is many-to-many: one table covers many hooks, and one hook is covered by many tables.

```c
struct nf_hook_ops {
	struct list_head	list;
	struct rcu_head		rcu;

	/* User fills in from here down. */
	nf_hookfn		*hook;
	struct net_device	*dev;
	void			*priv;
	u8			pf;
	enum nf_hook_ops_type	hook_ops_type:8;
	unsigned int		hooknum;
	/* Hooks are ordered in ascending priority. */
	int			priority;
};
/**
 * xt_hook_ops_alloc - set up hooks for a new table
 * @table:	table with metadata needed to set up hooks
 * @fn:		Hook function
 *
 * This function will create the nf_hook_ops that the x_table needs
 * to hand to xt_hook_link_net().
 */
struct nf_hook_ops *
xt_hook_ops_alloc(const struct xt_table *table, nf_hookfn *fn)
{
	unsigned int hook_mask = table->valid_hooks;
	uint8_t i, num_hooks = hweight32(hook_mask);
	uint8_t hooknum;
	struct nf_hook_ops *ops;

	if (!num_hooks)
		return ERR_PTR(-EINVAL);

	ops = kcalloc(num_hooks, sizeof(*ops), GFP_KERNEL);
	if (ops == NULL)
		return ERR_PTR(-ENOMEM);

	for (i = 0, hooknum = 0; i < num_hooks && hook_mask != 0;
	     hook_mask >>= 1, ++hooknum) {
		if (!(hook_mask & 1))
			continue;
		ops[i].hook     = fn;
		ops[i].pf       = table->af;
		ops[i].hooknum  = hooknum;
		ops[i].priority = table->priority;
		++i;
	}

	return ops;
}
```
Five is the maximum for one table (mangle). Across all tables you have many more:

```sh
mangle table  →  5 ops  (all hooks)
filter table  →  3 ops  (LOCAL_IN, FORWARD, LOCAL_OUT)
nat table     →  4 ops  (PREROUTING, POST_ROUTING, LOCAL_OUT, LOCAL_IN)
```

`Nat table `(`valid_hooks = 11011`, 4 bits set — bits 0, 1, 3, 4 for PRE_ROUTING, LOCAL_IN, LOCAL_OUT, POST_ROUTING) — but recall `nat` does not use `xt_hook_ops_alloc` at all, it defines its ops manually because each hook needs a different priority (`NAT_DST` vs `NAT_SRC`). `xt_hook_ops_alloc `assigns the same priority to all ops, which `nat` can't use.

So `num_hooks` is always just how many ops to allocate, and `hooknum` is always the actual bit position — they only stay in sync when there are no gaps in the bitmask (like mangle).

Each `nf_hook_ops` has a priority field that controls the order it runs at a hook relative to other registrations.
`xt_hook_ops_alloc` does this:
`ops[i].priority = table->priority;  // same value for every op`
It takes one priority from the table and stamps it on every op it creates. So all hooks get the same priority.

But nat needs two different priorities:

```sh
PREROUTING and LOCAL_OUT need NAT_DST priority (-100)
POSTROUTING and LOCAL_IN need NAT_SRC priority (300)
```
Because `DNAT` (changing destination) must happen early, and `SNAT` (changing source) must happen late. They can't both have the same priority.
`xt_hook_ops_alloc `has no way to express that — it only reads one `table->priority` value. So nat skips it entirely and defines the ops array by hand:

- `DNAT at PREROUTING` — for incoming packets whose destination needs rewriting before routing
- `DNAT at LOCAL_OUT` — for locally generated packets whose destination needs rewriting before routing
- `SNAT at POSTROUTING` — for all outgoing packets (forwarded or local) whose source needs rewriting
- `SNAT at LOCAL_IN` — for packets arriving at the local machine whose source needs rewriting

`DNAT always runs before the routing decision, regardless of which path`

```sh

OUTPUT (nat):      DNAT for packets created BY this machine
                   (kubelet, kube-proxy, or local pod calls a Service)
```

That's why `KUBE-SERVICES` appears in both `PREROUTING` and `OUTPUT` in your iptables

```sh
1. Pod → Service → Pod (same network)
   DNAT: yes (ClusterIP → pod IP)
   SNAT: no  (source is already a pod IP, return path works)

2. Node → Service → Pod
   DNAT: yes (ClusterIP → pod IP)
   SNAT: yes (source is node IP, need MASQ so reply goes through iptables)

3. External → NodePort → Pod
   DNAT: yes (node IP:30000 → pod IP:80)
   SNAT: yes (so the reply goes back through the node, not directly to client)

4. Pod → external API (Stripe, etc.)
   DNAT: no  (destination is a real internet IP, no rewrite needed)
   SNAT: yes (pod IP is private, needs NAT gateway to rewrite source)

5. Pod → Pod directly (no Service)
   DNAT: no
   SNAT: no
```

When the **first packet** of a new connection hits `KUBE-SVC-xxx`, iptables checks each rule one by one, top to bottom:
```sh

  Rule 2: is random < 0.50? → Pod 2
  Rule 3: → Pod 3

  Rule 1:    is random < 0.001? → Pod 1
  Rule 2:    is random < 0.001? → Pod 2
  Rule 3:    is random < 0.001? → Pod 3
```

```sh
Hooks:   PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING
         ─── fixed, can't add or remove ───

Tables:  raw, mangle, nat, filter
         ─── fixed, can't add or remove ───

Chains:  built-in chains are fixed (one per hook per table)
         BUT you can create custom chains ✓
```

Custom chains don't do anything by themselves — they only run when a built-in chain has a rule that jumps to them:
```sh

  rule: jump to KUBE-SERVICES (custom)    ← this is the connection
```

The `-s <podIP>/32` matches only when the source IP equals the pod's own IP — meaning the pod is talking to its own service (hairpin traffic):

`Pod (10.0.0.5) → ClusterIP → KUBE-SVC → KUBE-SEP → DNAT back to 10.0.0.5`
Without masquerade, the packet would arrive at the pod with source IP = 10.0.0.5 (itself). The pod would reply directly to itself, bypassing conntrack, and the connection would break. The mark causes `KUBE-POSTROUTING` to `SNAT` the source IP to the node IP, so the reply travels back through conntrack correctly.

When a rule does `-j KUBE-MARK-MASQ`, iptables jumps into that chain, executes it, then returns back to the next rule in `KUBE-SEP`:
```sh
KUBE-SEP-<hash>
  Rule 1: -s 10.0.0.5/32 -j KUBE-MARK-MASQ   ← jump in, set mark, come back
  Rule 2: -p tcp -j DNAT --to-destination ...  ← execute next
```  
So MARK and DNAT both happen inside the same chain, sequentially.

from the host's perspective, a pod sending a packet is the same as an external machine sending a packet in — it arrives on the vethXXX interface and hits `PREROUTING`.

```sh
src=10.0.0.6 → lands in KUBE-SEP-AAA
```

When pod A on Node 1 talks to pod B on Node 2, Node 1 is literally routing that packet. The packet goes through the `FORWARD `hook
```sh
KUBE-FORWARD
  1. --ctstate INVALID                        → DROP    # drop broken conntrack packets
  2. --mark 0x4000/0x4000                     → ACCEPT  # allow marked (masqueraded) traffic
  3. --ctstate RELATED,ESTABLISHED            → ACCEPT  # allow return traffic
```
Why rule 2 matters: Linux nodes default `FORWARD` policy is often `DROP`. Without this rule, NodePort and cross-node pod traffic — which gets marked by `KUBE-MARK-MASQ` — would be dropped when forwarded. The mark essentially serves a dual purpose: triggers `SNAT` at `POSTROUTING` AND grants `FORWARD` permission here.

Why rule 3 matters: Only the first packet of a connection needs to match rule 2. Subsequent packets in an established connection match rule 3 via conntrack, so they don't need the mark.

After DNAT, the kernel makes a routing decision based on the new (rewritten) destination. That determines FORWARD vs INPUT:
```sh
PREROUTING (DNAT rewrites dst)
        │
   routing decision
        │
   ┌────┴────┐
   │         │
FORWARD    INPUT
   │         │
   │    local process
   │    (no POSTROUTING)
   │
POSTROUTING  ← SNAT/MASQUERADE happens here
   │
out interface
```
INPUT — new dst is the node itself (a process on the node):

`external → NodePort → DNAT → dst=localhost:8080 (some local process) → INPUT → no POSTROUTING` 
`FORWARD `— new dst needs to leave via another interface (pod or another node):
```sh
client → DNAT → dst=10.0.0.5 (pod) → FORWARD → POSTROUTING → vethXXX → pod
client → DNAT → dst=10.0.0.6 (pod on other node) → FORWARD → POSTROUTING → eth0 → Node 2
```
`the mark set in PREROUTING only matters for forwarded traffic`
The mark is consumed in two places, serving two different purposes:
- KUBE-FORWARD (filter table, FORWARD hook):
`-A KUBE-FORWARD --mark 0x4000/0x4000 -j ACCEPT`
Purpose: grant forwarding permission. Linux default FORWARD policy is DROP. This lets marked packets bypass that.

- KUBE-POSTROUTING (nat table, POSTROUTING hook):
```sh
-A KUBE-POSTROUTING  ! --mark 0x4000/0x4000  -j RETURN   # not marked → skip
-A KUBE-POSTROUTING  -j MARK --xor-mark 0x4000            # clear the mark
-A KUBE-POSTROUTING  -j MASQUERADE                         # do SNAT
```
Purpose: trigger SNAT.

Hairpin is specifically when a pod gets routed back to itself through its own service. Step by step:

Setup:
```sh
Pod A = 10.0.0.5:8080
Service ClusterIP = 10.96.10.5:80
KUBE-SVC has only one endpoint → Pod A
```
- Step 1 — Pod A sends to the ClusterIP:`src=10.0.0.5  dst=10.96.10.5:80`
- Step 2 — PREROUTING on the host:
```sh
KUBE-SERVICES → KUBE-SVC → KUBE-SEP-AAA

In KUBE-SEP-AAA, two rules fire sequentially:
  Rule 1: -s 10.0.0.5/32 → KUBE-MARK-MASQ   ← src matches pod's own IP → mark set
  Rule 2: DNAT --to-destination 10.0.0.5:8080 ← dst rewritten

Packet is now: src=10.0.0.5  dst=10.0.0.5:8080  mark=0x4000
```
- Step 3 — routing decision: `dst=10.0.0.5` is a local address (pod on this node) → goes to FORWARD → POSTROUTING
- Step 4 — POSTROUTING: mark found → MASQUERADE → src rewritten to node IP:
```sh
src=192.168.1.10 (nodeIP)  dst=10.0.0.5:8080
```
- Step 5 — Pod A receives the request:
```sh
src=192.168.1.10  dst=10.0.0.5:8080
```
Pod A replies to the node IP — packet goes back through the host → conntrack reverses both SNAT and DNAT → Pod A gets the response from 10.96.10.5:80 ✓

**Without the mark/masquerade, why it breaks**:
```sh
src=10.0.0.5  dst=10.0.0.5:8080   ← pod receives packet from itself
```
Pod A replies directly to itself (loopback), bypassing the host network stack entirely → conntrack never sees the reply → can't reverse the DNAT → connection hangs forever.

The mark exists purely to fix this one problem: ensuring the reply packet goes back through the host so conntrack can clean up the NAT transformations.

The distinction is whether the host owns the IP or just has a route to it.
- INPUT fires when dst = an IP assigned to a host interface:
```sh
eth0 = 192.168.1.10  ← host OWNS this IP → INPUT
lo   = 127.0.0.1     ← host OWNS this IP → INPUT
```
- FORWARD fires when dst = an IP the host has a route to but doesn't own:
```sh
10.0.0.5 → via vethXXX   ← host has a ROUTE to it → FORWARD
```
The pod's IP 10.0.0.5 is assigned to eth0 inside the pod's network namespace — not to any interface in the host namespace. The host only has a route entry pointing to `vethXXX`:
```sh
$ ip route
10.0.0.5 dev vethXXX scope link    ← route, not a local address
```
So the kernel sees dst=10.0.0.5, looks up the routing table, finds "send it out vethXXX" — that's a forwarding decision, not local delivery → FORWARD.
```sh
Host owns:          192.168.1.10 → INPUT
Host routes to:     10.0.0.5     → FORWARD → vethXXX → pod netns
```
This is why every pod-to-pod packet on the same node still goes through FORWARD — the node is always acting as a router between network namespaces, even locally.

For pod A → pod B on the same node it's two different veths:
```sh
Pod A netns                Host netns                Pod B netns
───────────                ──────────                ───────────
eth0 ──→ vethAAA ────→ [FORWARD] ────→ vethBBB ──→ eth0
          (in)                           (out)
```          
The host is literally a router between network namespaces — packet arrives on one interface, routing table says "send out another interface", FORWARD fires in between.

Inside the pod's network namespace, 10.0.0.5 is assigned to eth0. When a packet arrives at the pod with: `src=10.0.0.5  dst=10.0.0.5:8080`
Pod A processes the request and replies:
`src=10.0.0.5:8080  dst=10.0.0.5`
Now dst=10.0.0.5 is the pod's own IP. Linux sees it as a local address in the pod's routing table:
```sh
$ ip route show table local (inside pod)
local 10.0.0.5 dev eth0   ← own IP is in local table
```
So the reply is delivered locally within the pod's network namespace — it never leaves through eth0, never crosses the veth pair, never reaches the host network stack.

 ```sh
-A KUBE-FORWARD -m conntrack --ctstate INVALID            -j DROP
-A KUBE-FORWARD -m mark --mark 0x4000/0x4000              -j ACCEPT
```

Purpose:
- INVALID → drop garbage packets (no valid conntrack state)
- ESTABLISHED → fast-path return traffic (skip per-rule evaluation)

`The NAT table has a built-in property you cannot see in any rule: the kernel only consults it for the first packet of a connection.`
```c
unsigned int
nf_nat_inet_fn(void *priv, struct sk_buff *skb,
	       const struct nf_hook_state *state)
{
	struct nf_conn *ct;
	enum ip_conntrack_info ctinfo;
	struct nf_conn_nat *nat;
	/* maniptype == SRC for postrouting. */
	enum nf_nat_manip_type maniptype = HOOK2MANIP(state->hook);

	ct = nf_ct_get(skb, &ctinfo);
	/* Can't track?  It's not due to stress, or conntrack would
	 * have dropped it.  Hence it's the user's responsibilty to
	 * packet filter it out, or implement conntrack/NAT for that
	 * protocol. 8) --RR
	 */
	if (!ct || in_vrf_postrouting(state))
		return NF_ACCEPT;

	nat = nfct_nat(ct);

	switch (ctinfo) {
	case IP_CT_RELATED:
	case IP_CT_RELATED_REPLY:
		/* Only ICMPs can be IP_CT_IS_REPLY.  Fallthrough */
	case IP_CT_NEW:
		/* Seen it before?  This can happen for loopback, retrans,
		 * or local packets.
		 */
		if (!nf_nat_initialized(ct, maniptype)) {
			struct nf_nat_lookup_hook_priv *lpriv = priv;
			struct nf_hook_entries *e = rcu_dereference(lpriv->entries);
			unsigned int ret;
			int i;

			if (!e)
				goto null_bind;

			for (i = 0; i < e->num_hook_entries; i++) {
				ret = e->hooks[i].hook(e->hooks[i].priv, skb,
						       state);
				if (ret != NF_ACCEPT)
					return ret;
				if (nf_nat_initialized(ct, maniptype))
					goto do_nat;
			}
null_bind:
			ret = nf_nat_alloc_null_binding(ct, state->hook);
			if (ret != NF_ACCEPT)
				return ret;
		} else {
			pr_debug("Already setup manip %s for ct %p (status bits 0x%lx)\n",
				 maniptype == NF_NAT_MANIP_SRC ? "SRC" : "DST",
				 ct, ct->status);
			if (nf_nat_oif_changed(state->hook, ctinfo, nat,
					       state->out))
				goto oif_changed;
		}
		break;
	default:
		/* ESTABLISHED */
		WARN_ON(ctinfo != IP_CT_ESTABLISHED &&
			ctinfo != IP_CT_ESTABLISHED_REPLY);
		if (nf_nat_oif_changed(state->hook, ctinfo, nat, state->out))
			goto oif_changed;
	}
do_nat:
	return nf_nat_packet(ct, ctinfo, state->hook, skb);

oif_changed:
	nf_ct_kill_acct(ct, ctinfo, skb);
	return NF_DROP;
}
```
The flow for NAT packets:
- `nf_nat_inet_fn` (the function actually registered at the hook for nat) checks the conntrack state
- `nf_nat_initialized(ct, maniptype)` checks if NAT translation was already decided for this connection
- Only if NOT yet initialized does it walk the nat table's rules ( the for loop)
-- Once a rule applies a NAT translation, it sets `IPS_SRC_NAT_DONE` / `IPS_DST_NAT_DONE` bits in `ct->status`
- For every subsequent packet of the same connection, `nf_nat_initialized` returns true → skip rule walking → apply the cached translation directly
So the NAT table's rules are consulted once per connection, on the first packet. After that, conntrack remembers the translation and applies it to all subsequent packets in both directions automatically — that's why reply packets get reverse-translated without you writing any reply rules.

`IP_CT_RELATED`, `IP_CT_RELATED_REPLY`, and `IP_CT_NEW` all share the same code block

Conntrack assigns one of these states to every packet based on where it sits in a connection's lifecycle:
- `IP_CT_NEW` — first packet of a connection, no matching entry in conntrack yet.

Example: the SYN packet of a new TCP connection, or the first UDP packet to a new destination.
- `IP_CT_ESTABLISHED` — a subsequent packet in the original direction of an already-tracked connection.

Example: client sends SYN (NEW), gets SYN-ACK back, then sends ACK and data — those data packets are ESTABLISHED.
- `IP_CT_ESTABLISHED_REPLY `— a packet in the reverse direction of a tracked connection.

Example: the SYN-ACK from the server, and all subsequent server-to-client packets.
- `IP_CT_RELATED` — a packet belonging to a different but related connection. Conntrack helpers identify these.

- `IP_CT_RELATED_REPLY` — the reply direction of a RELATED connection.

Comment in code says "Only ICMPs can be `IP_CT_IS_REPLY"` because most RELATED traffic is one-way ICMP errors.
Lifecycle of a typical TCP connection:
```sh
client → server  SYN          IP_CT_NEW
server → client  SYN-ACK      IP_CT_ESTABLISHED_REPLY  (first reply marks ct as confirmed)
client → server  ACK          IP_CT_ESTABLISHED
client → server  data         IP_CT_ESTABLISHED
server → client  data         IP_CT_ESTABLISHED_REPLY
...
```
the values you can use with -m conntrack --ctstate:

| State | Meaning |
|---|---|
| `NEW` | First packet of a connection (no entry yet, or entry exists but reply not seen) |
| `ESTABLISHED` | Packet belongs to a connection where traffic has been seen in both directions |
| `RELATED` | Packet related to but not part of an existing connection (e.g. ICMP errors, FTP data channel) |
| `INVALID` | Packet doesn't belong to any tracked connection and isn't a valid new connection (malformed, out-of-window TCP, etc.) |
| `UNTRACKED` | Packet was explicitly marked `NOTRACK` in the raw table — conntrack never processed it |
| `SNAT` | Connection had its source address translated |
| `DNAT` | Connection had its destination address translated |

Conntrack already created the entry before DNAT ran — DNAT just fills in the translation details on that existing entry.

Every conntrack entry stores two tuples — one for each direction:
```sh
nf_conn {
    tuplehash[ORIGINAL] = src+dst+ports of packets going one way
    tuplehash[REPLY]    = src+dst+ports of packets going the other way
}
```
The reply tuple is what reply packets are expected to look like — that's the key.
*Without DNAT — say client 1.1.1.1 connects to server 2.2.2.2:80*:
```sh
nf_conn {
    ORIGINAL:  src=1.1.1.1:5000  dst=2.2.2.2:80
    REPLY:     src=2.2.2.2:80    dst=1.1.1.1:5000
}
```
The reply tuple is just the original with src/dst swapped — no translation, packets come back exactly addressed how you'd expect.

*With DNAT — same client, but a rule rewrites destination 2.2.2.2:80 → 10.0.0.5:8080*:
```sh
nf_conn {
    ORIGINAL:  src=1.1.1.1:5000  dst=2.2.2.2:80      ← what client sent
    REPLY:     src=10.0.0.5:8080 dst=1.1.1.1:5000    ← what backend will reply with
    status:    IPS_DST_NAT bit set
}
```
The reply tuple's source got rewritten to the new destination (10.0.0.5:8080), because that's what the backend will use as its source when replying. The reply tuple effectively encodes "incoming reply packets will look like this — match them and undo the NAT before delivering."

*With SNAT — say internal 192.168.1.10 masquerading to public 5.5.5.5, talking to 2.2.2.2:80*:
```sh
nf_conn {
    ORIGINAL:  src=192.168.1.10:5000  dst=2.2.2.2:80   ← what internal client sent
    REPLY:     src=2.2.2.2:80         dst=5.5.5.5:5000 ← what server will reply to
    status:    IPS_SRC_NAT bit set
}
```
The reply tuple's destination got rewritten to the public address

```c
	/* Part of an established connection (either direction). */
	IP_CT_ESTABLISHED,

	/* Like NEW, but related to an existing connection, or ICMP error
	   (in either direction). */
	IP_CT_RELATED,

	/* Started a new connection to track (only
           IP_CT_DIR_ORIGINAL); may be a retransmission. */
	IP_CT_NEW,

	/* >= this indicates reply direction */
	IP_CT_IS_REPLY,

	IP_CT_ESTABLISHED_REPLY = IP_CT_ESTABLISHED + IP_CT_IS_REPLY,
	IP_CT_RELATED_REPLY = IP_CT_RELATED + IP_CT_IS_REPLY,
	/* No NEW in reply direction. */

	/* Number of distinct IP_CT types. */
	IP_CT_NUMBER,

	/* only for userspace compatibility */
#ifndef __KERNEL__
	IP_CT_NEW_REPLY = IP_CT_NUMBER,
#else
	IP_CT_UNTRACKED = 7,
#endif

	/* It's an expected connection: bit 0 set.  This bit never changed */

	IPS_ASSURED_BIT = 2,

	IPS_CONFIRMED_BIT = 3,

	/* Connection needs src nat in orig dir.  This bit never changed. */
	IPS_SRC_NAT_BIT = 4,

	IPS_DST_NAT_BIT = 5,
```

#### Why IPVS is replacing iptables for massive clusters
In a cluster with 10,000 Services, `kube-proxy` creates tens of thousands of these `iptables` rules. Because `iptables` evaluates rules sequentially (top to bottom), routing a packet becomes `O(n)`. Every new service makes the network slightly slower.

To fix this, pros switch `kube-proxy` to IPVS mode. IPVS is a highly optimized load balancer built into the Linux kernel that uses hash tables (`O(1)` lookup), so routing takes the exact same amount of time whether you have 10 Services or 100,000 Services.

### LoadBalancer (Uses an External REAL IP)
Kubernetes itself does not have a native load balancer for external traffic. If you create a Service of type LoadBalancer, Kubernetes delegates the job to the Cloud Provider (AWS, GCP, Azure) via the Cloud Controller Manager.
